================================================================================
SEZIONE 1 — CONTESTO ARCHITETTURALE
================================================================================

Il sistema è composto da:
  • ESP32 ("fermentatore F1") — termostato hardware autonomo con firmware custom V3
  • Home Assistant — pannello di monitoraggio, avvio fermentazioni e notifiche email
  • Mosquitto — broker MQTT locale (addon HA, localhost:1883)
  • InfluxDB + Grafana — storicizzazione opzionale

L'ESP32 è AUTONOMO: riceve il profilo una volta, poi gestisce tutto localmente.
HA non manda comandi periodici. Si limita a:
  1. Rispondere alla richiesta di profilo all'accensione dell'ESP32
  2. Inviare comandi manuali (avvia, stop)
  3. Monitorare lo stato via MQTT
  4. Inviare email di allarme

ATTENZIONE: questo documento descrive la versione V3 del firmware.
Esiste una versione V2 parzialmente implementata nei file esistenti — quella
logica è OBSOLETA. I file V2 vanno aggiornati o sostituiti come indicato.


================================================================================
SEZIONE 2 — DIFFERENZE CRITICHE V2 → V3
================================================================================

La differenza più importante riguarda il flusso di avvio:

V2 (vecchio, obsoleto):
  HA invia il profilo via MQTT push quando l'operatore preme "Avvia".
  L'ESP32 aspetta passivamente il comando su fermentazione/f1/cmd/avvia.

V3 (nuovo, da implementare):
  L'ESP32 all'avvio CHIEDE il profilo a HA pubblicando su:
    fermentazione/f1/richiedi_profilo
  HA deve ascoltare questo topic e rispondere su:
    fermentazione/f1/cmd/profilo

  Questa inversione è fondamentale: permette all'ESP32 di riprendere
  automaticamente dopo un riavvio hardware senza intervento umano.

Topic cambiati:
  V2: fermentazione/f1/cmd/avvia   → V3: fermentazione/f1/cmd/profilo
  V2: (nessun pull)                → V3: fermentazione/f1/richiedi_profilo (nuovo)

Il topic fermentazione/f1/cmd/stop è invariato.
Il topic fermentazione/f1/stato è invariato nel nome ma aggiunge il campo
"stato_fsm" (stringa: RUNNING / STANDBY / HOLDING / ALLARME / WIFI / MQTT / ecc.)

SEZIONE 4 — PROTOCOLLO MQTT COMPLETO
================================================================================

Broker: Mosquitto addon HA, localhost:1883, senza autenticazione.
Client ID ESP32: "esp32_f1_v3"
Buffer massimo payload accettato dall'ESP32: 4096 byte

────────────────────────────────────────────────────────────────────────────────
4.1  ESP32 → HA  (topic in ascolto su HA)
────────────────────────────────────────────────────────────────────────────────

fermentazione/f1/richiedi_profilo
  Pubblicato dall'ESP32 subito dopo aver sincronizzato NTP.
  HA ha 15 secondi per rispondere su fermentazione/f1/cmd/profilo.
  QoS: 1  |  retain: false
  Payload: { "ts": <unix_epoch_uint32>, "client": "esp32_f1_v3" }

fermentazione/f1/stato
  Heartbeat periodico ogni 60s. retain=true.
  QoS: 0  |  retain: TRUE
  Payload:
  {
    "temp_reale":    <float>     temperatura DS18B20 in °C
    "setpoint":      <float>     temperatura target corrente in °C
    "step_nome":     <string>    nome step corrente (o nome stato FSM)
    "step_index":    <int>       indice 0-based step (-1 se non RUNNING)
    "ore_step":      <float>     ore trascorse nello step corrente
    "ore_totali":    <float>     ore totali dall'avvio profilo
    "riscaldatore":  <bool>      true se relè riscaldatore ON
    "refrigeratore": <bool>      true se relè refrigeratore ON
    "allarme":       <bool>      true se stato = ALLARME_SENSORE
    "profilo":       <string>    nome profilo attivo ("nessuno" se STANDBY)
    "stato_fsm":     <string>    RUNNING / STANDBY / HOLDING / ALLARME /
                                 WIFI / MQTT / RICHIESTA_PROFILO
  }

fermentazione/f1/ack
  Conferma eventi ciclo vita.
  QoS: 0  |  retain: false
  Payload: { "stato": <string>, "profilo": <string>, "uptime_s": <uint> }
  Valori "stato":
    "avviato"            → profilo accettato e fermentazione avviata
    "fermato"            → CMD stop eseguito
    "profilo_completato" → tutti gli step terminati, ESP32 passa in HOLDING
    "errore_parsing"     → payload profilo non valido (JSON malformato o
                           campo "steps" assente/vuoto)

fermentazione/f1/allarme
  Evento di errore o notifica sistema.
  QoS: 1  |  retain: false
  Payload: { "tipo": <string>, "durata_minuti": <int>, "uptime_s": <uint> }
  Valori "tipo":
    "sensore_offline"    → DS18B20 non valido da N minuti. Relè spenti.
                           ESP32 attende 30s poi si riavvia (ESP.restart()).
    "riavvio_in_corso"   → pubblicato 500ms prima del riavvio hardware.
                           Usare per notifica email o log.
    "esp32_offline"      → Last Will Testament: il broker lo pubblica
                           automaticamente se l'ESP32 si disconnette senza
                           avvisare (crash, perdita alimentazione).

fermentazione/f1/pong
  Risposta al CMD ping.
  QoS: 0  |  retain: false
  Payload: { "free_heap": <uint>, "uptime_s": <uint>, "wifi_rssi": <int> }

────────────────────────────────────────────────────────────────────────────────
4.2  HA → ESP32  (topic pubblicati da HA)
────────────────────────────────────────────────────────────────────────────────

fermentazione/f1/cmd/profilo
  Risposta alla richiesta dell'ESP32. Pubblicare entro 15s da richiedi_profilo.
  QoS: 1  |  retain: false

  CASO A — Fermentazione attiva: invia profilo completo.
  {
    "profilo":                <string>    nome profilo (max 31 caratteri)
    "avvio_epoch":            <uint32>    Unix timestamp avvio fermentazione
    "isteresi":               <float>     banda morta relè in °C  (default 0.3)
    "min_cycle_minutes":      <uint>      protezione compressore   (default 5)
    "allarme_timeout_minuti": <uint>      watchdog sensore in min  (default 5)
    "steps": [
      { "step": <string>, "temp": <float>, "duration_hours": <float> },
      { "step": <string>, "temp": <float>, "ramp_hours":     <float> },
      ...
    ]
  }

  REGOLE sui steps:
    - duration_hours: step a temperatura COSTANTE per quella durata
    - ramp_hours: interpolazione LINEARE dalla temp dello step precedente
      alla "temp" di questo step, nell'arco di ramp_hours ore
    - Ogni step deve avere SOLO UNO dei due campi (mai entrambi)
    - Max 20 step, campo "steps" non può essere vuoto
    - Durate in ORE (float). I file JSON dei profili usano days →
      la conversione è responsabilità di HA via script Python

  CASO B — Nessuna fermentazione attiva.
  { "stato": "nessun_profilo", "temp_standby": <float> }
  (temp_standby opzionale, default 18.0°C sull'ESP32)

fermentazione/f1/cmd/stop
  Ferma il processo. ESP32 spegne relè, cancella profilo da NVS, va in STANDBY.
  QoS: 1  |  retain: false
  Payload: { "motivo": "operatore" }  (il contenuto è ignorato dall'ESP32)

fermentazione/f1/cmd/temp_standby
  Aggiorna temperatura di standby al volo (ha effetto immediato).
  QoS: 0  |  retain: false
  Payload: { "temp": <float> }

fermentazione/f1/cmd/ping
  Richiesta diagnostica. L'ESP32 risponde su fermentazione/f1/pong.
  QoS: 0  |  retain: false
  Payload: {}

--- [CRITICA - NUOVA] Risposta alla richiesta profilo ---

id: v3_f1_rispondi_richiesta_profilo
Trigger: MQTT topic fermentazione/f1/richiedi_profilo
Descrizione:
  Quando l'ESP32 si avvia e chiede il profilo, HA deve rispondere con:
  - Il profilo completo (se input_text.f1_profilo_attivo != "Nessuno")
  - Il messaggio "nessun_profilo" (altrimenti)

Logica:
  Condizione A: states('input_text.f1_profilo_attivo') not in
                ['Nessuno','','unknown','unavailable']

  Action A (profilo attivo):
    → Eseguire shell_command che chiama avvia_fermentazione.py con:
      - profilo  = states('input_text.f1_profilo_attivo')
      - avvio_epoch = states('input_number.f1_avvio_epoch') | int
      - isteresi = 0.3
      - allarme_timeout = 5
    → Il payload viene pubblicato su fermentazione/f1/cmd/profilo

  Action B (nessun profilo):
    → mqtt.publish
      topic: fermentazione/f1/cmd/profilo
      payload: '{"stato":"nessun_profilo","temp_standby":18.0}'
      qos: 1

  NOTA IMPORTANTE: avvio_epoch deve essere il timestamp ORIGINALE di avvio
  della fermentazione, NON now(). Deve essere salvato in input_number.f1_avvio_epoch
  quando l'operatore avvia la fermentazione (vedi script f1_avvia_fermentazione).
  Se fosse now() ogni riavvio ESP32 ricomincerebbe il profilo da capo.

--- [NUOVA] Notifica email riavvio in corso ---

id: v3_f1_riavvio_in_corso
Trigger: MQTT topic fermentazione/f1/allarme + tipo == "riavvio_in_corso"
Action: Email notify.fermentazione_email con titolo "[INFO] F1 - Riavvio ESP32"
  Testo: ESP32 si sta riavviando a causa di un allarme sensore.
  La fermentazione riprenderà automaticamente al riavvio.
  Profilo attivo: {{ states('input_text.f1_profilo_attivo') }}
  Ore totali trascorse: {{ states('sensor.f1_ore_totali') }}h

--- [ESISTENTE DA AGGIORNARE] ACK avvio profilo ---

id: v3_f1_ack_avvio_ricevuto  (era v2_f1_ack_avvio_ricevuto)
Trigger: MQTT fermentazione/f1/ack + stato == "avviato"
Action:
  - input_text.f1_profilo_attivo = trigger.payload_json.profilo
  - persistent_notification: "Fermentazione avviata: <profilo>"
  (invariato rispetto V2, solo aggiornare l'id)

--- [ESISTENTE, INVARIATO] ACK stop ---

id: v3_f1_ack_stop_ricevuto
Trigger: MQTT fermentazione/f1/ack + stato == "fermato"

  - input_number.f1_avvio_epoch = 0
  - persistent_notification stop

--- [ESISTENTE, INVARIATO] Allarme sensore DS18B20 offline ---

id: v3_f1_allarme_sensore
Trigger: MQTT fermentazione/f1/allarme + tipo == "sensore_offline"

--- [ELIMINARE in V3] Sensore ripristinato ---

id: v2_f1_sensore_ripristinato_email

SEZIONE 6 — SCRIPT DA IMPLEMENTARE
================================================================================

--- f1_avvia_fermentazione ---
Quando l'operatore vuole avviare manualmente una nuova fermentazione.

sequence:
  1. variables:
       profilo_nome:  states('input_select.f1_profilo_scelto')
       avvio_epoch:   as_timestamp(now()) | int

  2. Salva avvio_epoch in input_number.f1_avvio_epoch
     → input_number.set_value: entity=input_number.f1_avvio_epoch, value=avvio_epoch
     CRITICO: questo valore verrà usato nelle risposte future alle richieste
     di profilo dell'ESP32 (anche dopo eventuali riavvii).

  3. Esegue shell_command.avvia_fermentazione con parametri:
     profilo=profilo_nome, avvio_epoch=avvio_epoch, isteresi=0.3, allarme_timeout=5
     → questo chiama avvia_fermentazione.py che pubblica su cmd/profilo

  4. persistent_notification: "Profilo inviato, attesa ACK..."

--- f1_stop_fermentazione ---
  1. mqtt.publish fermentazione/f1/cmd/stop QoS:1
  2. input_text.f1_profilo_attivo = "Nessuno"
  3. input_number.f1_avvio_epoch = 0
  4. persistent_notification stop

--- f1_ping_esp32 ---
  mqtt.publish fermentazione/f1/cmd/ping payload:{}

--- f1_test_email ---
  Invia email di test con stato attuale sensori (invariato da V2)
